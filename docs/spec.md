## TL;DR

LoopOS is **one Claude account per company**, where every operator (human or AI agent) connects via MCP and shares the same durable backend. The backend is the Company Brain. Every resolved ticket sharpens it. Every new rule ships through Lightsprint as a PR.

- **Frontend:** Claude (the chat app) on each operator's device, plus a thin Next.js dashboard for the operator-of-operators (Ben).
- **MCP layer:** Reboot — exposes durable methods as `mcp=Tool()` so any Claude client can call them. State is shared across all operators.
- **Backend:** Reboot durable workflow. `User`, `Property`, `OpsTicket`, `SkillArtifact`, `Rule`, `BrainSource` as durable objects.
- **Model layer:** TokenRouter. Two-tier routing (fast OSS for triage, Claude Opus for reasoning), tagged per-property for cost telemetry.
- **Build/ship layer:** Lightsprint. New rules and skills ship as PRs from plan-mode prompts generated by LoopOS itself. Closing the loop literally.

This is YC RFS #2 (AI-native service company), #4 (Company Brain — executable skills file), and #15 (AI OS for Companies — closed loop) **in one product**.

## Components

### 1. Company Claude Account (the entry point)

One Claude app account per LoopOS customer. Each operator on the team is added as a workspace member (or in v0, all share via shared MCP credentials). When any operator opens Claude, the LoopOS MCP server exposes the same set of tools:

- `report_issue(audio_url | text, property_hint?)`
- `look_up_property(query)`
- `find_brain_sources(question)`
- `dispatch_vendor(ticket_id, vendor, cost_cap)`
- `resolve_ticket(ticket_id, outcome, actual_cost)`
- `propose_rule(title, trigger, action)`

These are not chatbot pleasantries — they are durable method calls. State persists across operators, devices, and sessions.

**Why "one account per company" not "one per operator":** the Company Brain needs *all* operator interactions to converge. Shirley's "I always use Lin HVAC for Taipei" and Haru's "the Ito vendor is slower in winter" are both knowledge — they only become a brain if they share a backend. Per-operator accounts re-fragment the knowledge LoopOS exists to consolidate.

### 2. Reboot — durable workflow & MCP layer

Per Reboot's Claude Code integration, methods decorated `mcp=Tool()` become MCP tools automatically. This is the magic seam: we write business logic once, and every Claude client gets it.

**Durable objects:**

| Object | Identifier | Holds |
|---|---|---|
| `User` | `user_id` (e.g. `shirley`) | name, lang, region, role, last-seen |
| `Property` | `property_id` (e.g. `warm_taipei_2br`) | display name, city, equipment, vendors, history index |
| `OpsTicket` | `ticket_id` | full lifecycle from ingest through resolve |
| `BrainSource` | `source_id` | one row per knowledge unit (voice memo, SOP, prior resolution) |
| `SkillArtifact` | `skill_name@version` | the executable skills file (YC #4 payoff) |
| `Rule` | `rule_id` | proposed or active automation |

**Reboot's `User` is the entry point.** Each operator's first MCP call constructs/loads their `User`. From there, methods like `User.report_issue(...)` create `OpsTicket` objects scoped to the right property.

### 3. Company Brain — a view, not a system

The brain is not a separate service. It's a queryable read-side over Reboot's durable state. Four layers:

| Layer | Source | Authoring path |
|---|---|---|
| `founder_voice_memo` | Ben recording 2-min memos via Claude voice input | Ben says "Claude, save this as a voice memo" → MCP tool `add_founder_memo()` |
| `structured_knowledge` | `Property` records, vendor cards, equipment specs | Synced from PMS (Beds24) + manual edits |
| `sop` | Markdown SOP files | Edited in Lightsprint, committed to repo, indexed on commit |
| `prior_resolution` | Resolved `OpsTicket` snapshots | Auto, on resolve |

**The "executable skills file" payoff (YC #4):** when a `Rule` is approved, a `SkillArtifact` is emitted as JSON, registered in Reboot, and exposed as a new MCP tool (`handle_hvac_leak`, `handle_late_checkout`, etc.). Tom Blomfield asked literally for this primitive. We render it on stage.

### 4. TokenRouter — the cost spine

Every LLM call from any path (operator MCP → Reboot method → reasoning step) routes through TokenRouter. Tagged with `user_id`, `property_id`, `ticket_id`, `tier`. Two practical effects:

- **TR dashboard groups by `property_id`** → cost-per-property accountability without us building anything.
- **`backend/usage.jsonl` is our local insurance** → the dashboard cost ticker reads local disk, never blinks if TR is slow on stage.

### 5. Lightsprint — the ship layer

LoopOS itself is hosted as a Lightsprint sandbox during the demo (or a Connect-Repository setup against `benikigai/loopos` if sandbox flakes). The closing cameo: a `Rule` we propose on stage becomes a Lightsprint plan-mode prompt → PR → live ship. Audience watches the company learn in real time.

```
   → marks ticket dispatched
   → posts vendor brief in zh-TW
   → notifies Ben if cost > $200 (it isn't, so silent)
```

| Tool | Caller | Effect |

## Three Es — key architectural choices

| Choice | Option A | Option B | Pick | Why |
|---|---|---|---|---|
| **MCP exposure** | Each operator gets own Claude account, share state via REST | One company Claude, all share via Reboot MCP | **B** | Brain converges. Reboot's `mcp=Tool()` is one decorator. Elegant > Efficient > Effective. |
| **Brain storage** | Vector DB (Weaviate/Qdrant) | Reboot durable objects + structured retrieval | **B for v0**, vector for v1 | Cuts a service. Demoable today. Add vector for cross-property fuzzy lookup later. |
| **Cost ticker source** | Read from TokenRouter dashboard API | Write local `usage.jsonl` and read it | **Local jsonl** | Stage-resilient. Insurance against TR slowness. |
| **Lightsprint role** | Optional dev tool | Required for closing demo cameo | **Required for demo, optional for prod** | Sponsor checkbox + it actually closes the loop visually. |
| **Operator auth** | Per-user OAuth via Reboot | Shared workspace token | **Shared today, per-user v1** | 3.5h doesn't fit OAuth. Single-tenant assumption holds for hackathon. |

## Open questions

- **Per-operator Claude workspaces vs. shared:** v0 is shared via single MCP credential. v1 needs Reboot to track operator identity per call. Confirm Reboot exposes caller identity on `mcp=Tool()` invocations — if not, sidecar a header.
- **Brain refresh policy:** SOPs are file-based, but founder memos and resolutions are append-only. Do we need brain compaction? Defer to v1.
- **Pricing model:** SaaS seats vs. per-property service fee vs. revenue share. Ben's instinct (and YC RFS #2) says service fee. Confirm before pitching to B-Capital partners post-demo.
- **Multi-tenant isolation:** when a second LoopOS customer signs up, do we run separate Reboot instances or one with tenant scoping? v1 question, not today.
